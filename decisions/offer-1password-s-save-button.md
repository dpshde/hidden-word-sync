# Offer 1Password's save button

Date: 2026-11-02

## Status

Accepted. Adds to [Unlock with a sync key kept in the password manager](unlock-with-a-sync-key-kept-in-the-password-manager.md).

## Context

The sync key has to end up in the person's password manager, and the person who started the project uses 1Password in Chrome. Even after the new-library form dispatched input events and really submitted, 1Password still didn't offer to save. A sign-up form whose password was generated by the page, never typed, is exactly the case its heuristics are least sure about.

1Password publishes a "Save in 1Password" button (`@1password/save-button`, MIT) for this case. The page hands the extension a save request (title, username, password, notes) directly, so nothing depends on heuristics. The button is a web component with no dependencies. The extension enables it; without the extension it stays disabled.

## Decision

The new-library screen shows 1Password's button above the form, filled with the library name, the sync key and a note naming the site.

- `bun run vendor` copies the published file into `public/vendor/onepassword-save-button.js`, like grab-bcv. The package is a pinned dev dependency.
- The button styles its shadow DOM with one fixed `<style>` block. The CSP allows that block by its SHA-256 hash, which `bun run vendor` computes and writes into `public/_headers`, rather than allowing inline styles.
- The element copies its save request to its inner button once, when it's added to the page, so renaming the library updates the inner button's `value`, as 1Password's documentation shows.
- If the button is still disabled two seconds after it's added, 1Password isn't installed, and the app hides it. It comes back if the extension enables it later.
- The form still submits as before, so other password managers, and 1Password's own detection, keep working.

## Consequences

- People with the 1Password extension get a save that doesn't depend on detection, with the item named "Hidden Word: <library>".
- It's code specific to one password manager, the first in the app. Others still rely on the form. Adding another vendor's button would follow the same pattern.
- Updating the button means bumping the version and running `bun run vendor`; the script refuses to update the CSP if the button's styles stop being one fixed block.
- The button's info icon links to 1Password's sign-up page. That link only shows with the extension installed.
- Whether the extension enables the button on this site can only be checked by hand.

## Update 2026-11-02, going on by itself

After saving with the button, people expected to go on without pressing Continue. 1Password's extension (8.12) doesn't tell the page that an item was saved. It does show its save dialog in a `<com-1password-modal>` element that it adds to the page and removes when the dialog closes (its notification element follows the same pattern, so the app watches both). After a click on the button, the app watches for that element to be added and then removed, and goes on as Continue would: the passkey prompt, then the library. The click on Save inside the dialog counts as a click on the page too, which lets the passkey prompt open. The page can't tell a save from a dismissal, so dismissing the dialog also goes on; the key is still under "Show sync key" in the menu. This relies on the extension's markup, not a documented interface, so if a 1Password update changes it, Continue still works.

## Update 2026-11-02, no passkey before going on

Closing 1Password's dialog now goes straight into the library, a second later so 1Password has finished writing the item. The passkey is offered on the library screen instead (see [the passkey update](unlock-with-a-sync-key-kept-in-the-password-manager.md#update-2026-11-02-passkey-after-creation)): iOS only offers to save a password for a submission the person started themselves, and running the passkey prompt first made Continue's submission a scripted one.

## Update, 2026-11-03: removed

Dylan asked to drop the button. Once the person pastes the new key into the form (see the sync-key decision), 1Password's own save offer appears, with the website filled in, so the button only duplicated it. The vendored `onepassword-save-button.js` and the code that watched its dialog are gone.
